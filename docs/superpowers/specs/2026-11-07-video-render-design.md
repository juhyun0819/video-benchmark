# Video Render — 설계 스펙

- 날짜: 2026-11-07 (2026-11-09 리뷰 반영)
- 상태: 리뷰 대기
- 관련 스펙: `2026-11-02-video-composer-mcp-design.md`

## 1. 목적

manifest를 실제 영상으로 합성해, 샘플 5개를 사람이 직접 보고 판단할 수 있게 한다. 전체 파이프라인에서 이 스펙의 위치는 다음과 같다.

1. manifest 생성 (완료)
2. **manifest로 영상 합성 (이 스펙)**
3. 영상을 보고 샘플을 수정한 뒤 5개를 고정한다
4. 합성으로 생기는 QA를 자동으로 만들기 위한 QA 카테고리를 정한다
5. 샘플 QA를 생성하고 사람이 검증한다
6. 시나리오를 짜고 대량 생성한다

## 2. 요구사항

### 합의된 결정

1. 벤치마크 영상은 전 구간 **1 fps**다. NextMe-800이 약 1 fps라서, 이벤트만 30 fps로 두면 화면 변화로 삽입 구간이 드러난다.
2. 벤치마크 영상에는 **오디오가 없다**.
3. 벤치마크 영상에는 **글자를 넣지 않는다**.
4. 샘플마다 벤치마크 영상과 검토 영상을 함께 만든다.
5. 검토 영상은 base를 8배속, 이벤트를 정속으로 재생하고 합성 시각, 블록 이름, caption을 표시한다.
6. 프레임은 1024×1024로 맞춘다.
7. 입력은 manifest뿐이다. 샘플을 고치면 새 manifest로 다시 실행한다.

### 기존 스펙에서 바뀌는 것

기존 스펙의 요구사항 6(원본 영상을 내려받지 않는다)은 샘플에 쓰는 원본에 한해 바뀐다. 샘플 5개에 필요한 파일만 `data/media/`에 받는다. 데이터셋 전체는 받지 않는다.

Ego4D는 2026-11-09에 라이선스가 승인됐다. 렌더러는 Ego4D 블록도 처리한다(§4). 현재 샘플 5개에는 Ego4D 블록이 없다. Ego4D ingest와 `config/categories.json` 매핑 확정은 이 스펙과 별도로 진행한다.

### 범위 밖

- QA 생성과 QA 카테고리 (영상을 본 뒤 별도 스펙)
- 원본 프레임에 원래 찍힌 글자. 요구사항 3은 렌더러가 글자를 덧붙이지 않는다는 뜻이다. base에는 논문 읽기, 스마트폰 영상 시청 구간이 있고 NextMe tar에는 `picture/ocr_text/`도 있다. 화면 글자에 근거한 QA를 어떻게 다룰지는 QA 스펙에서 정한다.
- 샘플 내용 수정
- 오디오
- MCP 도구, UI
- 대량 생성을 위한 병렬 처리

## 3. 구성

새 패키지 `@vb/render`를 추가한다. `@vb/core`의 `ManifestSchema`로 입력을 검증하고, `ffmpeg`, `ffprobe`, `tar`를 자식 프로세스로 실행한다. 새 npm 의존성은 추가하지 않는다.

| 파일 | 역할 |
|---|---|
| `plan.ts` | manifest에서 프레임 계획을 만드는 순수 함수 |
| `nextme.ts` | NextMe 프레임 이름 파싱, 가장 가까운 프레임 찾기, tar 추출과 캐시 |
| `video.ts` | 영상 프레임 시각 목록 읽기, 가장 가까운 프레임 고르기, 추출 |
| `media.ts` | 블록의 원본 파일 경로 찾기, 빠진 원본 검사 |
| `subtitles.ts` | 검토 영상용 ASS 자막을 만드는 순수 함수 |
| `ffmpeg.ts` | `ffmpeg`, `ffprobe` 실행 래퍼와 인코딩 설정 |
| `render.ts` | 전체 흐름 |
| `cli.ts` | `npm run render` 진입점 |

실행 방법:

```bash
npm run render -- --manifest data/exports/883d71cd-r3.manifest.json
npm run render -- --manifest <path> --only review
```

`--only`는 `benchmark` 또는 `review`다(§6). 데이터 루트는 ingest와 같이 `--data`, `VIDEO_BENCH_DATA_DIR`, 기본값 `./data` 순서로 정한다.

## 4. 원본 배치

| 데이터셋 | 위치 | 찾는 방법 |
|---|---|---|
| NextMe-800 | `data/media/nextme/<media.tar>` | manifest의 `media.tar` 경로 그대로 |
| Ego-Exo4D | `data/media/egoexo/<media.path>` | manifest의 `media.path` 경로 그대로 |
| HD-EPIC | `data/media/hdepic/` 아래 | `<video_id>.mp4`를 재귀로 찾는다 |
| Ego4D | `data/media/ego4d/` 아래 | `<video_id>.mp4`(video_uid)를 재귀로 찾는다 |

HD-EPIC과 Ego4D manifest에는 `media.path`가 없다. 다운로더가 만드는 폴더 구조에 기대지 않도록 파일 이름으로 찾는다. 같은 이름이 둘 이상이면 오류다.

Ego4D는 Lab22 CLI로 샘플에 쓰는 video_uid만 받는다. 출력이 1024×1024라서, 짧은 변이 540인 `video_540ss`는 약 2배로 늘려야 한다. 그래서 원본 해상도(`full_scale`)를 받는다. CLI 옵션 이름은 §11에서 확인한다.

## 5. 프레임 계획

합성 시각 `t`초마다 프레임 1장을 쓴다. 프레임 수는 `N = ceil(duration)`이고, `n = 0 … N-1`에 대해 `t = n`이다.

1. `composed_start ≤ t < composed_end`인 블록을 찾는다.
2. 원본 시각은 `src = src_start + (t - composed_start)`이다. 기존 재매핑 규칙과 같다.

블록의 프레임 수는 그 블록 구간에 들어가는 정수 `t`의 개수다. 블록 경계가 소수라서, 같은 길이의 블록이라도 앞뒤 위치에 따라 1장 차이가 날 수 있다.

### NextMe (base)

확인한 사실(`2026-04-15_1323-1709.tar`):

- `picture/masked/`에 JPEG 13,589장이 있다. 원본은 2880×2880이고 장당 약 2.7MB다.
- 파일 이름은 `2026-04-15_HH-MM-SS_HKT__frame_NNNNN.jpg`다. 프레임 번호 `n`의 시각은 정확히 `13:23:04 + n초`이고, 빠진 초, 같은 초에 두 장인 경우, 번호와 시각의 순서가 어긋난 경우가 모두 없다.
- 첫 프레임 시각(13:23:04)은 manifest의 `start_wallclock`, 즉 caption에서 구한 `recording_start`와 같다. 둘 다 HKT 벽시계다.
- tar 안의 순서는 시간순이 아니다(대체로 역순이다).

규칙:

- 프레임 시각은 파일 이름의 촬영 시각에서 읽는다. 위 녹화에서는 번호와 시각이 1:1이지만 다른 녹화에서도 그렇다는 보장이 없으므로 번호를 시간으로 쓰지 않는다.
- `start_wallclock + src`에 가장 가까운 프레임을 쓴다. 차이가 같으면 번호가 작은 쪽을 쓴다.
- 차이가 2초를 넘으면 그 구간을 리포트의 `gaps`에 남긴다. 렌더링은 계속한다.

캐시:

- `picture/masked/`의 JPEG를 1024×1024로 줄여 `data/media/nextme/frames/<video_id>/`에 캐시한다. 샘플 5개가 이 캐시를 함께 쓴다. 캐시 JPEG는 `ffmpeg -q:v 2`로 저장한다.
- 원본을 한 번에 다 풀면 임시 공간이 약 36GB 든다. 그래서 파일 목록을 500장씩 나눠 `tar -x -T <목록>`으로 임시 폴더에 풀고, 줄여서 캐시에 쓴 뒤 그 묶음의 원본을 지운다.
- 모든 프레임을 쓴 뒤 캐시 폴더에 `.complete`(원본 tar 경로, 크기, 프레임 수)를 쓴다. `.complete`가 있고 내용이 현재 tar와 맞을 때만 캐시를 다시 쓴다. 없거나 다르면 캐시를 지우고 처음부터 만든다.

### 영상 (이벤트)

원본 시각과 프레임을 맞추는 규칙:

- 원본 시각 0은 영상 스트림의 첫 프레임이다. 프레임 `k`의 원본 시각은 `pts_k − pts_0`이다. `pts_0`(ffprobe의 스트림 `start_time`)이 0이 아니면 리포트에 남긴다.
- 프레임 시각 목록은 `ffprobe`로 패킷 pts를 읽어 만든다(디코딩하지 않는다). 가변 frame rate 영상도 같은 규칙으로 처리한다.
- 각 `src`에 대해 원본 시각이 가장 가까운 프레임을 쓴다. 차이가 같으면 앞 프레임을 쓴다. NextMe와 같은 규칙이다.
- `src`가 마지막 프레임 시각보다 늦어도, 그 차이가 한 프레임 간격(`1 / media.fps`) 이하이면 마지막 프레임을 쓰고 리포트의 `clamped`에 남긴다. 메타데이터의 `duration_sec`과 실제 스트림 길이가 몇 프레임 다를 수 있기 때문이다. 차이가 그보다 크면 오류다.

추출:

- 블록마다 `ffmpeg`를 한 번 실행한다. 블록의 첫 프레임 앞으로 이동하고(`-ss`, `-copyts`), `select` 필터로 고른 pts의 프레임만 남긴다. `-ss`와 `fps=1`을 조합하는 방식은 fps 필터의 반올림 때문에 한 프레임씩 어긋날 수 있어서 쓰지 않는다.
- 뽑은 프레임은 렌더링 작업 폴더에 두고, 끝나면 지운다.
- 정사각형이 아닌 원본은 비율을 유지하고 검은 여백을 넣는다. Ego4D가 여기에 해당한다(가로형 영상이 많다).

### 회전

1. `ffmpeg`는 원본의 회전 메타데이터(display matrix)를 기본으로 먼저 적용한다.
2. 그 다음 데이터셋별 설정값(0, 90, 180, 270)만큼 더 돌린다. 기본값은 0이다. 원본을 받아 프레임을 확인한 뒤 값을 정한다. Ego-Exo4D와 HD-EPIC은 둘 다 Aria 안경으로 찍었지만 배포 형태가 달라 따로 확인한다.

리포트에는 메타데이터 회전과 설정 회전을 둘 다 남긴다.

## 6. 결과물

`data/renders/<composition_id>-r<revision>/` 아래에 쓴다.

| 파일 | 내용 |
|---|---|
| `benchmark.mp4` | H.264, 1024×1024, 1 fps, 프레임 `N`장, 오디오 없음 |
| `review.mp4` | H.264, 1024×1024, 8 fps, 자막을 영상에 입힘, 오디오 없음 |
| `review.ass` | 검토 영상의 자막 원본 |
| `render.json` | 리포트 |

### 인코딩

벤치마크 영상의 화질은 실험 조건이므로 고정한다. 두 영상 모두 다음 설정을 쓴다.

| 항목 | 값 |
|---|---|
| 코덱 | `libx264`, `-preset medium`, `-crf 18` |
| 픽셀 형식 | `yuv420p` |
| 키프레임 간격 | 벤치마크 60프레임(1분), 검토 영상 64프레임(8초) |
| 기타 | `-movflags +faststart`, 오디오 스트림 없음(`-an`) |

설정값은 `render.json`에 남긴다. 첫 샘플을 렌더링한 뒤 파일 크기와 화질을 보고 crf를 다시 정할 수 있다. 바꾸면 이 표를 고친다.

### 쓰기와 덮어쓰기

1. 같은 폴더 아래 임시 폴더 `.<composition_id>-r<revision>.tmp-<pid>/`에 모든 파일을 쓴다.
2. 결과 폴더가 이미 있으면 `.<…>.old-<pid>/`로 이름을 바꾼다. 비어 있지 않은 폴더 위로는 rename이 되지 않기 때문이다.
3. 임시 폴더를 결과 폴더 이름으로 바꾸고, `.old` 폴더를 지운다.

중간에 실패하면 임시 폴더를 지우고, 2단계 뒤라면 `.old` 폴더의 이름을 되돌린다. 남은 `.tmp-*`, `.old-*` 폴더는 다음 실행에서 지운다.

### `--only`

- 지정한 영상과 그 부속 파일만 새로 만든다(`review`이면 `review.mp4`, `review.ass`).
- 기존 결과 폴더에 다른 영상이 있고, 그 `render.json`의 manifest 경로와 `created_at`이 이번 manifest와 같으면 그 영상을 새 폴더로 옮겨 온다. 다르면 옮기지 않는다.
- `render.json`은 항상 새로 쓰고, 이번 실행에서 만든 파일과 옮겨 온 파일을 `outputs`에 구분해 적는다.

### 리포트

`render.json`에는 다음이 들어간다.

- manifest 경로, `composition_id`, revision, `created_at`
- 프레임 수, 블록별 프레임 수
- 원본 시각과의 최대 차이(블록별, 전체)
- `gaps`(NextMe), `clamped`(영상), 영상별 `pts_0`
- 회전(메타데이터, 설정), 인코딩 설정
- `outputs`

## 7. 검토 영상

벤치마크 영상과 같은 프레임을 쓴다. 8 fps로 고정하고, base 프레임은 1장씩, 이벤트 프레임은 같은 프레임을 8번 넣는다. 그래서 base는 8배속, 이벤트는 정속이 된다. 합성 시각에서 검토 영상 시각으로 바꾸는 계산은 순수 함수로 둔다. 샘플 5개의 길이는 32~44분이다(계산 결과 32.1~43.6분).

화면 위쪽에는 합성 시각, 역할과 카테고리, 블록 요약을 표시한다. 화면 아래쪽에는 caption을 표시한다.

| 구간 | 표시할 caption |
|---|---|
| base | `L2` |
| 이벤트 | `narration` 또는 `atomic`. 다음 caption까지, 최대 5초 표시 |
| 이벤트에 위 둘이 없을 때 | `keystep` |

caption 원문은 그대로 쓴다. ASS 특수 문자는 표시할 때만 이스케이프한다. 글꼴은 Noto Sans다(서버에 설치돼 있음).

## 8. 실패 처리

- `ffmpeg`, `ffprobe`, `tar`가 없거나 `ffmpeg`에 `libx264`, `libass`가 없으면 시작하지 않는다.
- 작업 전에 모든 블록의 원본을 검사하고, 빠진 파일을 한 번에 모두 보여 준 뒤 종료한다.
- 같은 revision을 다시 렌더링하면 덮어쓴다(§6). 완성된 프레임 캐시는 다시 만들지 않는다.
- 프레임 이름을 해석할 수 없으면 그 파일 이름을 보여 주고 종료한다.
- 필요한 원본 시각이 영상 끝을 한 프레임 넘게 지나면, 블록, 필요한 시각, 실제 마지막 프레임 시각을 보여 주고 종료한다.
- `ffmpeg`가 실패하면 stderr 마지막 부분을 보여 주고 임시 파일을 지운다.

## 9. 검증

자동 테스트는 `ffmpeg`로 만든 합성 영상과 합성 manifest만 쓴다. 실제 데이터는 저장소에 넣지 않는다. `ffmpeg`가 없으면 테스트를 건너뛰지 않고 실패시킨다.

- 프레임 계획: 소수점 블록 경계, 마지막 프레임, 블록 사이 이동, 블록별 프레임 수
- NextMe: 시간순이 아닌 입력, 동률, 2초 초과 구간, 묶음 단위 추출, `.complete`가 없거나 맞지 않는 캐시 재생성
- 영상 추출: 프레임 색으로 시각을 인코딩한 합성 영상에서 다음을 확인한다
  - 뽑힌 프레임이 가장 가까운 프레임 규칙과 맞는다(소수 `src`, 동률)
  - `pts_0`이 0이 아닌 영상
  - 가변 frame rate 영상
  - 끝을 한 프레임 이내로 넘는 경우(`clamped`)와 그보다 많이 넘는 경우(오류)
- 회전과 여백: 회전 메타데이터가 있는 가로형 합성 영상에서 방향과 검은 여백
- 결과물: 프레임 수, fps, 해상도, 픽셀 형식, 오디오 스트림 없음을 `ffprobe`로 확인
- 덮어쓰기: 기존 결과 폴더 교체, 실패 시 복구, `--only`에서 옮겨 오는 조건
- 검토 영상: 시각 변환, 자막 시각, caption 선택 규칙, 이스케이프
- 실패: 빠진 원본 목록, 원본 길이 초과, 필요한 인코더 없음

실제 샘플에서는 다음을 확인한다.

- 샘플 5개의 프레임 수가 `ceil(duration)`과 같다
- 블록 경계 앞뒤 프레임이 올바른 원본에서 나왔다
- `gaps`, `clamped`, 최대 차이, 파일 크기를 사용자에게 보고한다
