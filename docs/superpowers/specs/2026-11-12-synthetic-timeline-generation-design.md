# 합성 장기 egocentric 타임라인 생성 설계 (영상 생성 파트)

- 작성일: 2026-11-12
- 상태: 구현 중
- 범위: 영상 생성(조합)만 다룬다. 주석/정보 추출과 QA 생성은 별도 프레임워크이며, 이 문서는 그 프레임워크와의 **인터페이스(계약)**만 정의한다.

---

## 1. 목적과 성공 기준

### 1.1 목적
실제 일상은 반복이 많다는 관점에서, **고정 루틴 + 변동 + 예외**로 구성된 한 사람의 장기(최소 4주) egocentric 타임라인을 기존 영상 클립을 조합해 만든다. 이 환경에서 기존 방법들이 반복 속에서 성능이 떨어지는지 보이고 그 이유를 분석하는 **평가 벤치마크**를 만드는 것이 1차 목표다. 학습 데이터 용도는 이번 범위가 아니다.

### 1.2 성공 기준
1. **contradiction 최소화**: 장소, 시간, 같은 날 연속성에 대한 모순이 규칙 검사를 모두 통과하고, 이음새 VLM 검사에서 걸리는 비율이 낮다.
2. **다양성**: 사람 10명 × 28일을 서로 다른 집/직장으로 만들 수 있다.
3. **scalable**: world 입력만 바꾸면 사람 수와 기간을 늘릴 수 있고, 다른 연구자가 자기 world, 템플릿, 데이터 bank로 생성할 수 있다.
4. **통제 가능성**: 반복 강도, 예외 빈도, 길이를 다이얼로 조절할 수 있어, 반복 강도만 바꾼 ablation이 가능하다.

### 1.3 비목표
- 생성 모델로 새 영상 프레임을 만드는 것
- 실제 생활 분포를 정밀하게 재현하는 것 (분포 일치가 아니라 다이얼로 통제한다)
- 렌더링된 영상의 공개 (manifest만 공개한다)
- 여러 날짜리 예외의 구현 (스키마에만 정의, 5.4 참고)

## 2. 확정된 결정 요약

| 항목 | 결정 |
|---|---|
| 벤치마크 구성 | 사람 10명. 사람마다 집과 직장이 다름 |
| 단위 | 하루 단위로 생성하고 타임라인으로 묶음. 기본 28일, 길이는 다이얼(최소 28일) |
| 클립 카테고리 | 집 / 일 / 밥 / 취미 (+ 보조 카테고리 이동) |
| 실내·실외 | 카테고리가 아니라 `setting` 속성: `home_indoor` / `venue_indoor` / `outdoor` |
| 고정 노드 | 집, 직장, 취미(1~3개), 단골 장소(소스가 있을 때만). 부엌은 기본값이 집 |
| 변동 | 밥 성향, 취미 등장 여부와 순서, 기상·취침 시각 |
| 예외 | 슬롯 예외와 하루 예외를 v1에서 구현. 여러 날 예외는 스키마에만 정의 |
| 소스 | YouTube 집 영상과 직업 영상. 집 크리에이터와 직업 크리에이터는 서로 다르며, world에서 노드마다 `person_source`로 따로 바인딩한다. 사람이 검수하고, 편집 없이 이어지는 1인칭 영상이며 서로 다른 날로 볼 수 있는 것만 사용 |
| 소스 자격 | 머리 착용 시점. 렌즈와 화각 차이는 렌더링에서 보정 |
| 일관성 수준 | 장소 일관성은 필수. 사람 수준의 차이는 verifier가 심한 경우만 거름 |
| 일정 생성 | 프로그램이 결정적으로 샘플링(템플릿 + 다이얼 + seed). LLM은 클립 선택만 담당 |
| 일정과 소스의 관계 | schedule은 소스와 무관한 **내용 명세**. 매칭 단계에서 데이터 bank의 클립을 찾음 |
| 매칭 실패 시 | 조건을 단계적으로 완화하고, 그래도 안 되면 해당 날만 재생성, 시도 한도를 넘으면 실패 |
| 공백 시간 | 영상에 넣지 않고 타임스탬프에만 더함. 전환 공백(공백 시간 표)과 미기록 공백(슬롯 안 남는 시간)을 구분. QA는 영상이 있는 구간에서만 만듦 |
| 시간 분포 근거 | world 상위 속성(국가, 직업, 성별, 연령대, 근무 형태)에 맞는 실제 응답자 한 명의 하루를 빌려옴(donor). 분포 소스는 플러그인(v1: ATUS 2025). 날 단계 흔들림, 반복 강도, 예외는 실험에서 조작하는 다이얼 |
| world 속성의 출처 | 랜덤이 아니라 바인딩된 크리에이터의 실제 속성 |
| verifier | 규칙 검사 후 이음새 부근만 VLM 검사 |
| 공개 형태 | manifest만 공개 (데이터셋, 영상 ID, 구간). 렌더링은 사용자 쪽 스크립트 |
| 재현성 기준 | manifest. manifest로부터의 렌더링은 결정적. 같은 schedule로 다시 매칭한 결과의 동일성은 보장하지 않음 |

## 3. 전체 구조

```
[사람 검수 + 정보 추출 프레임워크]  (범위 밖, 계약은 4.1)
        │  승인된 원본 영상 (원본 영상 1개 = 하루 1개), 활동 구간별 내용 명세
        ▼
① ingest → catalog (데이터 bank)
        ▼
② world: 사람별 profile, 고정 노드, 다이얼, seed
        ▼
③ schedule 생성기 (결정적, 소스와 무관)
        │  schedule.json = 날별 슬롯 목록. 슬롯 = 내용 명세 + 시간 범위
        ▼
④ 매칭 (노드 바인딩 → 하드 필터 → LLM 선택 → 완화 사다리 → 타임스탬프 배정)
        ▼
⑤ verifier (규칙 검사 → 이음새 VLM 검사 → 실패 시 ④로 되돌림)
        ▼
⑥ timeline manifest (공개 대상, 영상 없음)
        ▼
⑦ 렌더링 스크립트 (사용자 쪽)
```

**contradiction 방지 담당**
- ③: 일정 수준의 모순 (출근일 구성, 예외 겹침)
- ④: 노드와 시간의 모순 (다른 집, 밤 슬롯에 아침 클립, 클립 재사용)
- ⑤: 남은 시각적 모순

### 3.1 기존 파이프라인과의 관계
- **유지**: ingest → catalog 구조, MCP 편집 방식(revision 증가, `expected_revision` 충돌 방지), provenance 보존, 참조한 후보가 없으면 쓰지 않고 실패하는 원칙
- **변경**: composition이 "base day 1개 + 슬롯 N+1개"에서 "사람 × N일 타임라인"으로 바뀜. manifest가 하루 단위에서 타임라인 단위로 바뀜. 렌더링 스펙은 7장으로 대체함
- **추가**: world, schedule 생성기, 노드 바인딩, 공백 시간 표, verifier

## 4. 데이터 모델

### 4.1 클립 내용 명세 (정보 추출 프레임워크와의 계약)
schedule의 슬롯과 catalog의 클립은 **같은 스키마**를 쓴다. 이 스키마가 두 프레임워크 사이의 계약이다.

```json
{
  "category": "meal",              // home | work | meal | hobby | transit
  "setting": "home_indoor",        // home_indoor | venue_indoor | outdoor
  "node": "home",                  // 추상 노드 (world 기준)
  "activity": "저녁 요리",          // 서술형, 매칭 순위에 사용
  "time_of_day": "evening",        // early_morning | morning | midday | afternoon | evening | night
  "tags": ["cooking", "kitchen"]   // 선택, 서술형 보조
}
```

catalog 클립은 여기에 다음을 더 가진다.

| 필드 | 설명 |
|---|---|
| `clip_id` | 고유 ID |
| `source` | 데이터셋 이름 (예: `youtube`) |
| `video_id` | 원본 영상 ID |
| `source_start_s`, `source_end_s` | 원본 영상 안의 구간 (초) |
| `day_group` | 원본 영상 ID. 같은 날 찍은 조각 묶음 |
| `person_source` | 크리에이터 또는 착용자 ID |
| `captions` | 추출 프레임워크가 만든 caption (원본 시각 기준) |
| `fingerprint` | 원본 영상 길이 + 프레임 몇 장의 perceptual hash |
| `extractor_version` | 추출 프레임워크 버전 |

**클립 단위**: 매칭 단위는 추출 프레임워크가 나눈 **활동 구간**이다. 원본 영상 전체는 `day_group`(같은 날 표시)으로만 쓴다.

### 4.2 world (사람 한 명)

```json
{
  "person_id": "p01",
  "attributes": {                       // 바인딩된 크리에이터의 실제 속성에서 가져옴 (랜덤 아님)
    "country": "US",
    "occupation_group": "construction_extraction",
    "sex": "male",
    "age_band": "25-34",
    "work_pattern": "day_shift"
  },
  "distribution_source": "atus_2025",   // 분포 소스 플러그인 (5.6)
  "donors": {                           // 5.6에서 뽑은 결과를 기록
    "weekday": {"case_id": "…", "backoff_level": "occupation_group"},
    "weekend": {"case_id": "…", "backoff_level": "all"}
  },
  "nodes": {
    "home":      {"kind": "home"},
    "kitchen":   {"kind": "kitchen", "default": "home"},
    "workplace": {"kind": "workplace", "job": "carpenter", "setting": "venue_indoor"}, // setting 기본값 venue_indoor. 실외 직업은 outdoor
    "hobby_1":   {"kind": "hobby", "activity": "러닝", "setting": "outdoor", "weekly_freq": 2},
    "frequent_1": {"kind": "frequent_place", "optional": true}
  },
  "meal_style": {                       // 사전값은 5.5의 ATUS 장소 비율 (eat_out = 식당 + 기타 장소), 사람마다 조정 가능
    "workday": {
      "lunch":  {"workplace": 0.84, "home": 0.10, "eat_out": 0.06},
      "dinner": {"home": 0.83, "eat_out": 0.09, "workplace": 0.07, "others_home": 0.01}
    },
    "rest_day": {                       // 주말·연차 등 근무하지 않는 날. 직장 식사 없음
      "lunch":  {"home": 0.67, "eat_out": 0.27, "others_home": 0.06},
      "dinner": {"home": 0.79, "eat_out": 0.14, "others_home": 0.07}
    },
    "breakfast_skip_prob": 0.3          // ATUS 기록 비율은 하한이라 설계값으로 둠
  },
  "dials": {
    "length_days": 28,
    "routine_strength": 0.7,
    "exception_rate": {"slot": 0.1, "day": 0.05},
    "wake_sleep": "default_v1"
  },
  "seed": 1234
}
```

- 취미는 1~3개.
- 단골 장소 노드는 바인딩할 소스가 있을 때만 활성화된다.
- `kitchen.default = home`이면 집 노드의 클립을 그대로 쓴다.

### 4.3 schedule.json (생성기의 출력, 소스와 무관)

```json
{
  "person_id": "p01",
  "generator_version": "…",
  "template_version": "…",
  "days": [
    {
      "day_index": 3,
      "weekday": "Thu",
      "day_type": "workday",          // workday | hobby_day | home_day | (예외로 바뀐 경우) leave_day 등
      "wake": "07:52",
      "sleep": "22:14",
      "exceptions": [],
      "slots": [
        {
          "slot_id": "d3-s1",
          "required": true,
          "window": ["07:52", "09:00"],
          "spec": {"category": "home", "setting": "home_indoor", "node": "home",
                   "activity": "출근 준비", "time_of_day": "morning"}
        }
      ]
    }
  ]
}
```

### 4.4 세 종류의 공백
영상이 없는 시간은 세 종류이며, 모두 영상에는 들어가지 않고 타임스탬프에만 반영된다. manifest는 영상이 없는 구간마다 종류(`transition` / `unrecorded` / `unscheduled`)를 기록한다.

| 종류 | 의미 | 시간 결정 방식 |
|---|---|---|
| 전환 공백 | 활동과 활동 사이, 장소가 바뀌는 시간 (예: 통근) | 공백 시간 표에서 샘플링 |
| 미기록 공백 | 슬롯의 활동은 계속되지만 영상이 없는 시간 (예: 9시~12시 근무 중 영상은 45분) | 슬롯 시간 범위에서 클립 길이를 뺀 나머지 |
| 일정 밖 시간 (`unscheduled`) | 두 슬롯 사이가 전환 공백보다 길게 남은 시간. 그 사람은 직전 슬롯의 장소에 머무는 것으로 본다 | 다음 슬롯 시작 − (직전 슬롯 끝 + 전환 공백) |

**공백 시간 표 (전환 공백)**
- `(이전 category·node → 다음 category·node)` 전환마다 분포를 가진다.
- 통근 전환(`home → workplace`, `workplace → home`)은 ATUS 경험 분위수(5.5)를 쓴다.
- 나머지 전환은 LLM이 초안을 한 번 만들고, 사람이 검토한 뒤 버전을 붙여 고정한다. 생성할 때 LLM을 다시 호출하지 않는다.
- 표에 없는 전환이 필요하면 생성을 실패시키고, 누락된 전환을 보고한다.

**QA 규칙**: QA는 영상이 있는 구간에서만 만든다. 세 종류의 공백 구간에 대해서는 질문을 만들지 않는다. (QA 프레임워크 쪽 규칙이지만, manifest가 영상 구간을 정확히 기록해서 이를 가능하게 한다.)

**기록 비율**: 날마다 (영상 길이 합 ÷ 깨어 있는 시간)을 계산해 manifest와 통계에 남긴다. NextMe-800의 39.5%와 비교하는 현실성 지표로 쓴다.

## 5. schedule 생성기 (③)

### 5.1 입력과 출력
- 입력: world, 카테고리 설정, 날 유형별 템플릿, 기상·취침 분포 설정, seed
- 출력: `schedule.json`
- **같은 입력이면 늘 같은 출력.** 데이터 bank를 참조하지 않는다.
- 다른 연구자는 world, 카테고리 설정, 템플릿을 바꿔서 쓸 수 있다.

### 5.2 단계
1. **달력**: 1~N일차를 평일과 주말로 구분
2. **날 유형**: 평일은 `workday`. 주말은 world의 취미 빈도에 따라 `hobby_day` 또는 `home_day`(청소 등 집안일)
3. **하루 예외 적용**: `exception_rate.day`에 따라 일부 날의 유형을 바꿈 (예: 평일 → 연차·병가, 주말형 템플릿 사용)
4. **기상·취침, 근무, 식사 시각: 두 단계**
   - **사람 단계 (world 생성 시 한 번)**: 5.6의 donor 방식으로 평일 donor와 주말 donor를 한 명씩 뽑고, 그 사람들의 실제 기상·출근·퇴근·식사 시각을 이 사람의 평균 일정으로 쓴다. 항목 사이의 상관관계(일찍 일어나는 사람이 일찍 출근함)가 그대로 유지된다.
   - **날 단계 (날마다)**: 그 평균 주변에서 작은 σ로 흔든다. σ는 반복 강도 다이얼에 연결한다 (강도 1 → 20분, 강도 0 → 45분, 초기값). ATUS는 응답자당 하루 기록이라 날 단계 σ의 근거가 되지 않는다. 이 값은 실험에서 조작하는 독립변수로 다룬다.
   - 기상 시각은 그날의 첫 필수 슬롯보다 빨라야 한다
5. **슬롯 나열**: 날 유형별 템플릿을 펼친다 (5.5의 수치를 사용).
   - 평일 (`workday`): `집(아침, 필수) → [전환: 통근] → 일(오전, 필수) → 밥(점심) → 일(오후, 필수) → [전환: 통근] → 밥(저녁, 필수) → 취미(빈도에 따라, 선택) → 집(저녁, 선택)`
     - 저녁 밥은 필수 슬롯이다 (ATUS 평일 근무일 저녁 기록 78%, 기록 누락 경향을 고려하면 실제로는 더 높음).
     - 집(저녁) 슬롯의 등장 확률은 0.91이다. 근거: 평일 근무자의 90.8%가 퇴근 후 취침 전까지 집에서 30분 이상 깨어 있는 활동(식사·이동 제외)을 함. 길이 중앙값 187분(IQR 105~270분), 여가 활동 30분 이상 77%, 집안일 30분 이상 46% (`atus2025_extra.json`).
     - 시간이 모자랄 때 줄이는 순서: 집(저녁) 길이 → 취미 길이 → 취미 제거 → 집(저녁) 제거. 필수 슬롯은 줄이거나 빼지 않는다. 참고로 퇴근 후 취침까지 쓸 수 있는 시간은 중앙값 330분, 하위 10%는 140분이다.
   - 주말 취미일 (`hobby_day`): `집(아침) → 밥(아침, 선택) → 취미(필수, 오전 중심) → 밥(점심) → 집(오후, 집안일 또는 휴식) → 밥(저녁) → 집(저녁)`
   - 주말 집안일 (`home_day`): `집(아침) → 밥(아침, 선택) → 집(집안일, 필수) → 밥(점심) → 집(휴식) → 밥(저녁) → 집(저녁)`
   - 주말에 사회적 외출(친구 집, 식당)은 슬롯 예외로 넣는다.
   - 밥 슬롯의 내용(집밥, 직장, 외식, 거르기)은 world의 `meal_style`에서 샘플링한다.
   - 슬롯 하나에 클립을 여러 개 넣을 수 있다. 가능하면 같은 `day_group`에서 고른다.
6. **반복 강도 적용**: `routine_strength`가 높을수록 선택 슬롯의 등장 여부, 순서, 시각이 날마다 같게 유지된다. 낮을수록 더 흔들린다. 구현에서는 사람별 "기준 하루"를 한 번 샘플링하고, 날마다 강도에 반비례하는 확률로 그 기준에서 벗어나게 한다.
7. **시간이 맞지 않는 선택 슬롯 정리**: 5번의 줄이는 순서대로 처리하고, 빠진 슬롯은 그 날의 `dropped_optional`에 기록한다.
8. **슬롯 예외 삽입**: 7번 **이후에** 남아 있는 슬롯 중에서 `exception_rate.slot`에 따라 슬롯 하나의 명세를 교체한다 (예: 저녁 밥 → 친구와 외식, `setting: venue_indoor`). 슬롯 정리 때문에 예외가 지워지는 일이 없도록 순서를 이렇게 둔다.
9. **검증 후 출력**: 예외끼리 겹치지 않는지, 시간 범위가 기상·취침 사이에 있는지 확인한다.

**실현값 기록 (다이얼과 실제 결과의 비교)**
- 반복 강도와 예외 빈도는 실험에서 조작하는 독립변수다. 조작한 값과 실제로 생성된 값이 다르면 ablation 해석이 흔들리므로, schedule과 manifest에 둘을 나란히 기록한다.
- `realized`: 슬롯 예외 비율(예외가 들어간 슬롯 수 ÷ 예외 후보 슬롯 수), 하루 예외 비율, 선택 슬롯별 등장률, 날 사이 슬롯 구성 일치도(반복 강도의 실측값), 매칭 단계에서 빠진 슬롯 수
- 생성 통계에는 다이얼 값별로 `realized`의 평균과 범위를 보고한다. 실험 결과는 다이얼 값이 아니라 `realized` 값을 x축으로 그릴 수도 있게 한다.

### 5.3 예외 정의

| 범위 | 대체 대상 | 예시 | v1 구현 |
|---|---|---|---|
| `slot` | 하루 안의 슬롯 하나 | 저녁을 친구와 외식 | 예 |
| `day` | 하루 전체의 템플릿 | 평일 연차, 병가 | 예 |
| `multi_day` | 연속된 여러 날 | 2일 여행, 주말 캠핑 | 아니오 (스키마만) |

- 모든 예외는 schedule과 manifest에 명시적으로 기록한다: `{scope, type, replaces, day_range}`. QA 프레임워크가 루틴이 깨진 지점을 알아야 하기 때문이다.
- 예외끼리는 겹치지 않는다.

### 5.4 multi_day 예외 (스키마만)
- 해당 기간에는 집과 직장 노드가 빠지고, **임시 고정 노드(여행지)**가 생긴다. 기간 내내 같은 여행지 노드를 써야 한다.
- 같은 사람의 연속된 여행 영상 소스가 확보되면 구현한다.

### 5.5 템플릿 수치 근거: ATUS 2025 (집계 참고값)
이 절의 집계 수치는 템플릿 구조(슬롯 순서, 주말 유형 비율, 예외 빈도 기본값)를 정하는 근거와, donor 방식이 실패할 때의 fallback(`schedule_defaults_atus2025.json`)으로 쓴다. 사람별 시각은 5.6의 donor에서 온다.
- 자료: ATUS 2025 microdata (Activity, Respondent 파일). 전일제 취업자(`TELFS=1`, `TRDPFTPT=1`), 가중치 `TUFINLWGT` 사용. 평일은 월~금 중 공휴일이 아닌 날(n=1,284), 주말은 토·일(n=1,313).
- 계산 스크립트와 결과: `scripts/atus/atus_stats.py`, `data/distributions/atus2025/atus2025_stats.json`, 응답자별 값 `data/distributions/atus2025/atus2025_stats_per_respondent.csv`. 설정 파일은 `config/schedule_defaults_atus2025.json`.
- 정의: 기상 = 기록 시작(04:00)부터 이어진 첫 수면 구간이 끝나는 시각. 취침 = 기록 끝까지 이어진 마지막 수면 구간이 시작되는 시각. 출퇴근 = 일터(`TEWHERE=2`)에서 한 근무 활동의 첫 시작과 마지막 끝. 통근 = 첫 근무 직전, 마지막 근무 직후에 이어진 이동 활동 길이의 합.

**사람 단계 분포 (사람마다 한 번 샘플링)**

| 항목 | 평일 | 주말 | 비고 |
|---|---|---|---|
| 기상 | 평균 06:26, σ 61분 | 평균 07:49, σ 82분 | 상하위 5% 제외. 중앙값 06:30 / 08:00 |
| 취침 | 평균 22:18, σ 67분 | 평균 22:18, σ 74분 | 주말 취침은 평일과 거의 같음 |
| 출근 시각 (주간 근무자) | 평균 07:34, σ 77분 | | 05:00~11:00에 출근한 사람만 (일터 근무자의 85%) |
| 근무 시간 (점심 제외) | 중앙값 500분, IQR 453~582분 | | 퇴근 = 출근 + 근무 시간 + 점심 |
| 통근 (편도) | 중앙값 20분, IQR 15~35분 | | 퇴근길도 거의 같음 (중앙값 20분, IQR 15~30분) |

- 주말 평균은 그 사람의 평일 평균에 차이(기상 +83분, 취침 0분)를 더한다.
- 처음 구상한 평일 08:00 기상, 22:00 취침과 비교하면 ATUS의 평일 기상이 약 1.5시간 이르다. 미국 전일제 취업자 기준이기 때문이며, 한국 기준이 필요하면 통계청 생활시간조사로 교체한다 (13장).

**직업별 출퇴근 (평일, n≥30만 사용)**

| 직업군 (TRMJOCC1) | n | 출근 중앙값 (IQR) | 퇴근 중앙값 (IQR) |
|---|---|---|---|
| 관리·경영·재무 | 162 | 08:00 (07:20~09:06) | 17:00 (16:00~17:45) |
| 전문직 | 252 | 07:45 (07:00~08:31) | 16:57 (15:45~17:30) |

직장 노드의 직업이 위 직업군에 대응하면 이 분포로 사람 단계 출근 시각을 뽑는다. 표본이 작은 직업군은 전체 분포를 쓴다.

**밥 (`meal_style` 사전값)**

| 끼니 | 평일 근무일: 기록 비율 / 시각 중앙값 (IQR) / 장소 | 쉬는 날 (주말 중 근무하지 않은 날, n=910): 기록 비율 / 시각 / 장소 |
|---|---|---|
| 아침 | 36% / 07:03 (06:10~08:55) / 집 69%, 직장 27% | 53% / 08:02 (07:15~09:00) / 집 86%, 식당 5% |

- 쉬는 날의 끼니 사전값은 **그날 근무하지 않은 응답자만으로** 계산한다 (`atus2025_extra.json`). 이전 판은 주말에 출근한 응답자(주말의 30%)까지 섞여 직장 식사가 들어가 있었고, 이는 쉬는 날과 모순이다. 연차·병가 같은 하루 예외에도 같은 사전값을 쓴다.

- ATUS는 짧은 식사를 덜 기록하는 경향이 있어서, "기록 비율"은 실제로 먹는 비율보다 낮을 수 있다. 끼니를 거를 확률로 그대로 쓰지 말고, 하한으로 참고한다.

**주말과 예외**
- 주말 스포츠·운동: 주말 하루의 18%에서 등장, 그중 실외 35%, 길이 중앙값 90분, 시작 시각 중앙값 10:45 → 취미일 템플릿의 취미 슬롯을 오전 중심으로 둔다.
- 주말 하루의 45%에서 집안일이 120분 이상 → `home_day`의 근거
- 주말 하루의 32%에서 사회적 외출(남의 집, 식당·야외 여가) → 주말 슬롯 예외의 기본 빈도
- 전일제 취업자의 평일 중 10%는 근무가 없음 → 하루 예외(`day`) 빈도의 상한 참고값. 기본값은 이보다 낮게 둔다 (휴가가 몰리지 않는 4주를 가정).
- 근무한 평일 중 27%는 일터 근무 기록이 없음(재택 추정). v1에서는 재택근무를 다루지 않는다.

### 5.6 donor 방식: 실제 응답자의 하루를 빌려오기

**원칙**: 사람의 기본 생활 리듬은 우리가 정하지 않는다. world 속성에 맞는 실제 시간 사용 조사 응답자의 하루에서 가져온다. 우리가 정하는 것은 실험에서 조작하는 다이얼(날 단계 σ, 반복 강도, 예외 빈도, 길이)뿐이다.

**분포 소스 플러그인**
- 인터페이스: `donor_pool(attributes, day_kind) → [(case_id, weight, day_profile)]`
- `day_profile` = 기상, 취침, 출근, 퇴근, 근무 시간, 통근, 끼니별 시각과 장소, 운동 여부·시각·실내외, 집안일 시간
- v1 구현: ATUS 2025 (`atus_stats.py`가 만드는 응답자별 표가 그대로 donor pool이 된다)
- 다른 국가나 연도는 같은 인터페이스로 소스를 추가한다 (예: 통계청 생활시간조사 microdata). world의 `country`와 맞지 않는 소스는 쓰지 않는다.

**donor 선택 절차**
1. **pool 필터**
   - 평일 donor: 평일(공휴일 제외)이고, 그날 일터에서 근무했으며, 기상·취침 시각이 정의되는 응답자. `work_pattern: day_shift`면 출근 05:00~11:00
   - 주말 donor: 토·일이고, 그날 근무하지 않았으며, 기상·취침 시각이 정의되는 응답자 (주말 템플릿은 쉬는 날이므로)
2. **단계적 후퇴 (backoff)**: 아래 순서로 조건을 걸어 보고, 가중 표본이 30명 이상인 첫 단계를 쓴다.
   1. 직업군 × 성별 × 연령대
   2. 직업군 × 성별
   3. 직업군
   4. 성별 × 연령대
   5. 전체 (전일제 취업자)
3. **가중 추출**: 그 단계의 pool에서 조사 가중치(`TUFINLWGT`)에 비례해 한 명을 seed로 뽑는다.
4. **기록**: 뽑힌 `case_id`와 사용한 backoff 단계를 world와 manifest에 남긴다.
5. **주말 일관성 확인**: 평일 donor와 주말 donor는 서로 다른 사람이다. 주말 기상이 평일 기상보다 2시간 넘게 이르면 주말 donor를 다시 뽑는다 (최대 5회, 초기값).

**donor 값이 범위를 벗어날 때**
- 허용 범위: 기상 04:00 이후, 취침 27:59(다음날 03:59) 이전, 그리고 템플릿이 요구하는 슬롯 순서가 성립하는 값 (예: 퇴근 후 취침까지 필수 슬롯이 들어갈 시간이 있음).
- 벗어나면 **값을 잘라내지 않고 donor를 다시 뽑는다** (같은 backoff 단계, 최대 5회, 초기값). 실제 응답자의 하루라는 주장을 지키기 위해서다.
- 5회 안에 못 찾으면 그때만 값을 범위 안으로 당기고, 어떤 항목을 얼마나 당겼는지 world와 manifest에 기록한다. 전체 생성에서 이 비율을 통계로 보고한다.

**donor 값이 비어 있는 항목**
- 예: donor가 그날 점심을 기록하지 않은 경우. 그 항목만 같은 backoff 단계의 다른 응답자 중 그 항목이 있는 사람에게서 가중 추출해 채운다 (그 단계의 경험 분포에서 뽑는 것과 같다). 어느 항목을 대체했는지 기록한다.
- 취미 시각: donor에게 운동 기록이 없으면(주말 쉬는 날 donor의 대부분) 취미 슬롯 시작 시각을 같은 backoff 단계에서 운동 기록이 있는 응답자의 시작 시각으로 채운다. 단계에 그런 응답자가 30명 미만이면 전체 pool의 분포(주말 운동 시작 중앙값 10:45, IQR 08:30~14:41)를 쓴다. 대체 여부를 기록한다.

**필요한 추가 자료**
- 성별과 연령은 ATUS Roster 파일(`atusrost-2025.zip`)에 있다. 현재 계산에는 Activity, Respondent 파일만 썼으므로, Roster 파일을 추가하면 backoff 1·2·4단계를 쓸 수 있다. 그 전까지는 3단계(직업군)와 5단계(전체)만 쓴다.

**ATUS 사용상 주의**
- 미국 응답자이므로 `country: US`가 아닌 사람에게 쓰려면 해당 국가 소스를 추가해야 한다. 소스가 없으면 생성을 시작하지 않고 실패한다 (명시적으로 `allow_country_fallback: true`를 준 경우만 ATUS로 대체하고 기록한다).
- donor 하루는 한 번의 관측이므로, 그날이 그 사람에게 특이한 날이었을 수도 있다. 날 단계 흔들림과 반복 강도로 다루며, 이 한계는 논문에 명시한다.

---

## 6. 매칭 (④)

### 6.1 노드 바인딩
world의 추상 노드를 bank의 실제 소스에 연결하는 설정이다. 예: `p01.home → youtube:creator_X / 집 영상`, `p01.workplace → youtube:creator_Y / 직업 영상`. schedule은 바인딩을 모른다.

### 6.2 하드 필터 (날짜 순서대로, 슬롯 순서대로)
다음을 모두 만족하는 클립만 후보가 된다.
1. `category`, `setting`, 바인딩된 `node`가 일치
2. 클립의 `time_of_day`가 슬롯 시간 범위와 맞음
3. 타임라인 전체에서 아직 쓰지 않은 클립
4. **원본 영상 하나(`day_group`)는 합성 타임라인의 하루에만 쓸 수 있음** (하드 규칙)
5. 클립 길이가 슬롯의 남은 시간 범위 안에 들어감

### 6.3 LLM 선택 (MCP)
- LLM에게 슬롯 명세, 상위 K개 후보의 요약(초기값 K=10), 최근 며칠 동안 고른 내역을 보여준다.
- 선호 규칙: 같은 날의 같은 노드 슬롯은 가능하면 같은 `day_group`에서 고른다.
- 반복 강도에 맞게 "어제와 비슷한 것"과 "다른 것" 중 무엇을 고를지 판단하게 한다.
- MCP 도구:
  - `list_slot_candidates(timeline_id, slot_id)`
  - `assign_clip(timeline_id, slot_id, clip_id, expected_revision)`
  - `unassign_clip(timeline_id, slot_id, expected_revision)`
  - `get_timeline(timeline_id)`
- 편집할 때마다 revision이 1씩 오르고, `expected_revision`이 맞지 않으면 덮어쓰지 않는다 (기존 방식 유지).
- 대량 생성은 같은 도구를 LLM 에이전트가 자동으로 호출하는 배치 모드로 돌린다.

### 6.4 완화 사다리
후보가 없을 때 순서대로 시도한다. 하드 필터 1, 3, 4는 절대 완화하지 않는다.
1. 서술형 필드(`activity`, `tags`) 무시
2. 시간 범위를 ±30분 확장 (초기값)
3. 해당 날만 하위 seed로 schedule을 재생성 (최대 5회, 초기값)
4. 실패: 타임라인을 쓰지 않고, 채울 수 없는 슬롯 목록을 보고

각 단계에서 무엇을 완화했는지 manifest의 클립 항목에 기록한다.

### 6.5 타임스탬프 배정
- 슬롯 사이: 다음 슬롯 시작 ≥ 직전 슬롯 끝 + 전환 공백 (공백 시간 표에서 seed로 샘플링). 다음 슬롯의 시간 범위 때문에 그보다 늦게 시작하면, 남는 시간은 일정 밖 시간(`unscheduled`)으로 기록한다 (4.4).
- 슬롯 안: 클립을 놓을 위치는 클립의 실제 촬영 시간대를 우선 따르고, 모르면 seed로 샘플링한다. 남는 시간은 미기록 공백이 된다.
- 클립 끝이 슬롯 범위나 취침 시각을 넘으면 6.4로 넘어간다.
- 합성 타임스탬프는 날짜(1~N일차)와 시각으로 표현한다.

## 7. verifier (⑤)

### 7.1 1단계: 규칙 검사 (모두 통과해야 함)
- **일정**: 날 유형 준수, 슬롯 시간 범위, 기상·취침 시각 범위, 클립 간 겹침 없음, 타임스탬프 단조 증가
- **노드**: 모든 클립의 소스가 바인딩된 노드에 속함
- **재사용**: 클립 중복 없음, `day_group` 하나가 하루에만 쓰임
- **교체 지점**: 같은 노드에서 연속된 두 클립이 서로 다른 `day_group`이면 표시 (활동 도중 교체 의심)
- **시간대**: 클립의 `time_of_day`와 배정된 시각이 맞음
- **예외**: 예외 기록과 실제 일정이 일치, 예외끼리 겹치지 않음

### 7.2 2단계: 이음새 VLM 검사
- `day_group`이 바뀌는 지점마다 앞뒤 3초(초기값)의 프레임을 VLM에 보여준다.
- 질문: 장소가 같은가 / 빛과 시간대가 이어지는가 / 손과 장신구가 같은가
- 기준 점수 미만이면 해당 슬롯을 다시 매칭한다 (6.4). 5회 실패하면 표시만 남기고 진행한다.
- 원본 영상에 접근할 수 있는 내부 환경에서만 실행한다.

### 7.3 출력
타임라인마다 `verifier_report.json`: 규칙별 통과 여부, 이음새별 점수, 재매칭 이력, 남은 표시 목록

## 8. timeline manifest (⑥, 공개 대상)

```
timeline manifest
├─ id, revision
├─ versions: schema, generator, template, gap_table, extractor
├─ inputs: world (attributes, donors 포함), dials, seed, node_binding, distribution_source
├─ days[]
│   ├─ day_index, weekday, day_type, wake, sleep, coverage_ratio, dropped_optional
│   ├─ no_video_spans[]: start, end, kind (transition | unrecorded | unscheduled)
│   ├─ exceptions[]: scope, type, replaces, day_range
│   └─ clips[]
│       ├─ source, video_id, source_start_s, source_end_s
│       ├─ synthetic_start, synthetic_end
│       ├─ slot_id, category, node, setting
│       ├─ relaxations[]
│       ├─ fingerprint
│       └─ provenance: 클립 내용 명세, 원본 caption, extractor_version
├─ captions[]: 합성 타임스탬프로 다시 매핑한 caption (시간순)
├─ realized: 다이얼별 실현값 (5.2)
├─ donor_adjustments: 재추출 횟수, 당긴 항목과 크기, 대체한 항목
├─ verifier_summary
├─ licenses: 소스별
└─ qa_tracks: (자리만, 기존 유지)
```

- **caption 재매핑**: 기존 규칙을 유지한다. 합성 시각 = 클립 합성 시작 + (원본 시각 − 클립 원본 시작). 클립 경계에 걸친 caption은 경계에서 자르고 `clipped` 표시를 붙인다.
- 저장 위치: `data/exports/<timeline_id>-r<rev>.manifest.json`
- 참조한 클립이 catalog에서 사라졌으면 쓰지 않고 실패한다 (기존 원칙 유지).

## 9. 렌더링 스크립트 (⑦, 사용자 쪽)

1. manifest를 읽는다.
2. 소스를 가져온다. YouTube는 사용자가 직접 다운로드하고, 라이선스 데이터셋은 사용자가 보유한 경로를 지정한다.
3. `fingerprint`를 확인한다. 영상이 없거나 hash가 다르면 **누락 보고서**를 만든다.
4. 정규화: 해상도, fps, 화각 crop과 왜곡 보정. 소스별 파라미터는 manifest에 고정한다.
5. 날마다 영상 파일 하나와 합성 시각 sidecar 파일을 출력한다. 공백은 영상에 들어가지 않으므로 시각은 sidecar로만 전달한다.
6. ffmpeg 버전과 파라미터를 고정해서 결정적으로 렌더링한다.

기존 문서의 렌더링 스펙("승인 대기")은 이 장으로 대체한다.

## 10. 오류 처리 원칙
- 조용히 넘어가지 않는다. 실패하면 산출물을 쓰지 않고, 무엇이 부족한지 보고한다.
- world 검증: 끼니별 장소 확률의 합이 0이거나 1이 아닌 경우(허용 오차 0.01), 취미가 0개이거나 4개 이상인 경우, 국가 소스가 없는 경우는 생성 전에 오류로 처리한다. 값을 조용히 무시하거나 빼지 않는다.
- schedule 생성 실패: 예외 겹침, 시간 범위 모순 → 생성기가 보고
- 매칭 실패: 완화 사다리를 모두 거친 뒤 채울 수 없는 슬롯 목록 보고
- 공백 시간 표에 없는 전환: 생성 실패와 누락된 전환 보고
- 렌더링 시 소스 누락: 누락 보고서. 일부 날만 렌더링할지는 사용자 옵션

## 11. 테스트 전략
- **실현값 기록**: 예외 빈도와 슬롯 등장률을 큰 값으로 설정해 생성했을 때, manifest의 `realized` 값이 실제 생성 결과를 세어 본 값과 일치하는지.
- **donor 재추출**: 범위를 벗어난 donor가 잘리지 않고 다시 뽑히는지. 5회 실패 시에만 당기고 기록되는지.
- **world 검증**: 끼니 확률 합이 0인 world가 오류로 거부되는지.
- **donor 선택**: 같은 seed면 같은 donor가 뽑히는지. 조건 칸의 표본이 30 미만일 때 다음 backoff 단계로 내려가는지. 가중 추출의 빈도가 가중치에 비례하는지(큰 반복 시행으로 확인). 국가 소스가 없을 때 실패하는지.
- **schedule 생성기**: 같은 입력이면 출력이 바이트 단위로 같은지. 반복 강도를 0과 1로 두었을 때 날 사이 슬롯 구성의 차이가 각각 최대와 최소인지. 예외가 겹치지 않는지.
- **매칭**: 작은 가짜 bank로 하드 필터와 `day_group` 규칙을 검증. 후보를 일부러 비워서 완화 사다리의 각 단계가 순서대로 작동하는지 확인. LLM 선택은 고정 응답을 주는 가짜 선택기로 대체해 테스트.
- **타임스탬프**: 단조 증가, 공백 샘플링의 결정성, 범위 초과 시 사다리 진입.
- **verifier 규칙 검사**: 규칙마다 위반 사례 fixture를 하나씩 두고 정확히 잡아내는지 확인.
- **manifest**: 스키마 검증, caption 재매핑과 clipping (기존 테스트 유지·확장).
- **렌더링**: 짧은 합성 테스트 영상으로 같은 manifest를 두 번 렌더링해 결과가 같은지 확인. fingerprint 불일치 시 누락 보고서가 나오는지 확인.

## 12. 분석 실험과의 연결 (설계에 미치는 요구사항)
- 같은 사람, 같은 클립 풀, 같은 이음새 조건에서 **반복 강도만 바꿔 생성**할 수 있어야 한다. 그래야 성능 저하의 원인을 합성 artifact가 아니라 반복으로 돌릴 수 있다.
- 선택 사항: 이음새만 보는 baseline (출처 데이터셋을 맞히는 단순 classifier)으로 QA가 풀리지 않음을 보인다.
- 선택 사항: NextMe-800 실제 90일 일부에서 같은 경향이 보이는지 확인한다.
- 선행연구 비교: X-LeBench는 Ego4D 클립과 합성 일정으로 life log를 만들지만, 여러 주에 걸친 반복과 날 사이 장소 일관성이 없다. 이 두 가지를 차별점으로 유지한다.

## 13. 열린 항목 (구현 전에 결정)
1. 공백 시간 표 중 통근 외 전환의 초안 작성과 검토 담당
2. VLM 이음새 검사에 쓸 모델과 기준 점수
3. 정보 추출 프레임워크의 출력이 4.1 스키마를 따르도록 맞추는 작업 (상대 프레임워크 쪽 일정)
4. 크리에이터 10명의 국가 분포. 미국 외 크리에이터가 있으면 해당 국가의 분포 소스(예: 통계청 생활시간조사 microdata)를 추가해야 한다
5. 날 단계 σ(반복 강도와 연결된 20~45분)의 근거. 실측 근거가 필요하면 NextMe-800 90일에서 같은 사람의 날마다 기상 시각 흔들림을 재서 쓸 수 있다
6. ATUS 표본 확대: 2023·2024년을 합칠지 (직업별 칸이 얇음). Roster 파일 추가 (5.6)
7. 크리에이터 속성(직업군, 성별, 연령대, 근무 형태)을 누가 어떻게 기록할지. 사람 검수 단계에서 같이 기록하는 것을 제안
